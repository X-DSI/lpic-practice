## Context
Questions are generated by Claude from the LPI Learning Materials, verified twice, reviewed by the
maintainer, and consumed by both interfaces. The format must be easy for a human to review, strict
enough for automated checks, and stable as the bank grows to 1,200+ questions for LPIC-1.

The real exams use three item formats: single-answer multiple choice, multiple-answer multiple
choice ("choose two"), and fill-in-the-blank.

## Options
- **YAML per objective, validated by JSON Schema plus a semantic validator** — reviewable, commentable,
  small diffs.
- **JSON only** — no comments; harder to review by eye.
- **One big file per exam** — painful diffs and merge conflicts; slow review.
- **Mocks as standalone question copies** — 600 copies per exam; a fix must be repeated everywhere.
- **Database as source of truth** — not reviewable in pull requests.

## Decision

### Files

| File | Schema | Purpose |
|---|---|---|
| `content/<exam>/objectives.yaml` | `schemas/objectives.schema.json` | Topics, objectives, weights, lesson counts |
| `content/<exam>/questions/<objective>.yaml` | `schemas/question-file.schema.json` | All questions for one objective |
| `content/<exam>/mocks/mock-NN.yaml` | `schemas/mock-exam.schema.json` | One mock exam: an ordered list of question IDs |

YAML is the authoring format (comments allowed, easy review). A build step (planned) compiles it to
JSON for the apps.

### Question fields

| Field | Required | Notes |
|---|---|---|
| `id` | yes | `<exam>-<objective>-<NNNN>`, permanent, never reused. 9000–9999 reserved for examples. |
| `type` | yes | `single_choice` · `multi_choice` · `fill_in` |
| `difficulty` | yes | 1–5, per `docs/difficulty-rubric.md` |
| `pool` | yes | `practice` (CLI drills) or `holdout` (mock exams only) |
| `stem` | yes | The question, Markdown |
| `exhibit` | no | Verbatim block shown under the stem (command output, config file) |
| `options` | choice types | 4–8 options, each with `id` (a–h), `text`, optional `rationale` (why right/wrong) |
| `answer` | choice types | Option IDs. Exactly 1 for single, 2+ for multi |
| `select_count` | multi_choice | How many to choose; must equal `len(answer)` |
| `fill_in` | fill_in | `accepted` answers, `match` mode (`exact`, `normalized`, `regex`), `case_sensitive` |
| `explanation` | yes | Original explanation shown after answering |
| `source` | yes | `material`, `material_version`, `objective`, `lesson` (+ optional `section`) — a reference, never copied text |
| `verify` | no | Shell check for command answers, run in a disposable container |
| `review` | yes | `status` (`draft` → `pass1` → `pass2` → `approved`) and `history` |
| `tags` | no | Free-form, e.g. commands covered |
| `retired` | no | `true` removes it from selection without deleting the ID |

`normalized` matching: trim, collapse internal whitespace; case-sensitive by default because Linux
commands are.

### Checks beyond JSON Schema

`tools/validate.py` also enforces what JSON Schema can't express:

- File `exam`/`objective` match the file path; each question ID matches the file.
- IDs unique across the whole exam.
- Option IDs unique; every `answer` refers to an existing option.
- `select_count == len(answer)` for multi-choice.
- Objectives' weights sum to 60.
- Mock exams: 60 unique IDs, all existing, all `holdout`, all `approved` (once `--strict`),
  per-objective counts equal objective weights, difficulty mix sums to 60.

## Consequences
- Every question is reviewable in a diff, traceable to its lesson, and checked by CI.
- `schema_version` is 1. Breaking changes need a superseding ADR and a version bump.
